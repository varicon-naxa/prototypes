Bills

What Mango Earthmoving does today

There is no on-charge field on a bill, so the recovery side is invisible. To track which subcontractor bills get passed on to their customers, they assign a Xero Project to the bill — a field that exists for something else entirely, used as a marker.

The workaround has a cost, and it is not the double handling

Assigning a Xero Project is what triggers the lines associated to a Project sync failures they keep raising. So the missing feature is not just an inconvenience — it is actively generating support tickets against the Xero integration. They have already confirmed Xero Tracking Categories do not meet the need, which is why they fall back to Projects.

Which means shipping this feature closes two things: the on-charge gap, and a class of sync failure whose root cause is a field being used for a purpose it was not built for.

What they actually want to know

Two questions, and the flag only answers the first:
  1. Which of these have I passed on to my customer? — a marker is enough.
  2. Did I recover all of it? — a marker cannot answer this, and it is the question that costs money when it goes wrong.

Option 1 — the flag, exactly as asked for

A status on the bill: Not on-charged → Ready for invoicing → Invoiced, set by hand, mirroring the Daywork Docket "mark as invoiced" flow. Filterable from the list. Nothing required in Xero. This is buildable quickly and it does answer the literal ask.

Before anything is revised, the flag is already $7,200 wrong

Fulton Hogan's $31,200 bill is ticked Invoiced, and only $24,000 of it was ever put on a claim — on-charged at less than cost, which is normal and often deliberate. The flag has no way to express that, so it rounds a partial recovery up to a full one. Nobody did anything wrong; the field cannot hold the truth. Then things get worse.
The problem is not day one — it is day ninety. The flag is a second, hand-maintained record of what was recovered, sitting next to the claims that actually recovered it. Press the button: Claim #4 on Little Collins gets revised down, as claims routinely are.

Option 2 — same screen, status derived from what was actually claimed

Identical UI for the user. The difference is underneath: the bill carries a link to the claim or invoice line that recovered it, and the status is computed from that link. The manual tick still exists — it becomes an override, and it is labelled as one, so you can always tell a judgement from a fact.

Rules this prototype commits to

The arguable ones are first. Everything here is a proposal, not a decision.

1"Not on-charged" and "never on-charging this" are different states.
A single blank status means both not yet and this is our own cost — so the list can never be worked to zero, because you cannot tell what is outstanding from what is finished. Excluded — own cost is an explicit state, set deliberately. Same principle as the ticket-expiry checkbox: a blank field must not carry a decision.
2The status is derived; the tick is an override, and it is labelled.
Where a bill is linked to a claim line, the status is computed. Where a person overrides it, the row says so. Two things that can disagree must never look identical — the whole failure mode here is a number nobody can adjudicate.
3Partial recovery is a first-class state, not a rounding error.
On-charging at less than cost is normal and often deliberate. A binary flag forces a lie in both directions. Partially on-charged with a shortfall figure is the honest answer.
4Terminology matches Daywork Dockets exactly.
Dockets already say "mark as invoiced". If Bills say something else for the same concept, that is a support cost forever. If the docket wording is wrong, change both — but do not add a second vocabulary.
5Nothing about on-charge status touches Xero.
The whole point is to stop the Xero Project workaround. If any part of this writes to Xero, the sync-failure class survives and the feature has not paid for itself.
6On-charge status never alters cost.
Committed, tracked and actual stay disjoint. An on-charged bill is still a cost — recovery is revenue, recorded on the claim. Netting the two on the cost side is how you get a $175,100 bill reported as $350,200.
7Bulk setting from the list, not one bill at a time.
A bookkeeper works a month of bills in one sitting. If marking twenty bills takes twenty drawers, they will keep using Xero. Same lesson as the construction-tickets page.
8Status changes are audited.
Who marked it, when, and whether the system or a person set it. This is money movement between a cost and a customer — it needs a trail.

Open questions — these need a call before build

Ordered by how much rework the wrong answer causes.

Is the link bill→claim line, or bill→claim? Line-level gives real shortfall figures and is what makes the whole thing worth building. Header-level is much cheaper and gives roughly nothing beyond the flag. This is the decision that determines whether option 2 is worth doing at all.
Does a bill split across multiple claims need to be modelled on day one? Real for long-running subcontracts. If yes, the link is many-to-many from the start and the data model must allow it — retrofitting that is expensive.
Who sets the link — the person coding the bill, or the person building the claim? Different people, different weeks, different habits. Whoever it is, the prompt has to sit in their existing flow or it will not happen.
Does an unrecovered on-charge bill need to chase someone? "Ready for invoicing" sitting untouched for six weeks is money nobody has billed. A flag is passive; this would make it active. Out of scope for the first cut, but it changes whether this is a bookkeeping marker or a revenue control.
Does on-charge status belong in the daily cost tracking view and the reporting epic (VDP-2425)? Likely yes for the register export. Confirm before building a second export path.

Recommendation

Build the option 2 shape, ship the option 1 experience. Mango gets the mark-as-invoiced control they asked for and stop assigning Xero Projects. Underneath, the status is a computed field with a manual override, and the bill→claim link starts as a nullable column that is set by hand. Nothing in the first cut requires the matching logic to be clever — it just has to be possible later without a rebuild, and without asking the customer to re-enter a year of history.
