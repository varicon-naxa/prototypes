What are you uploading?

Two different things share the word "ticket". Say which one up front and every later step changes to match.
Worker tickets
The licences and certificates your people hold — a row per worker per ticket. This is the register on the Tickets page.
Ticket types (the catalogue)
The list of tickets that exist in your tenant — code, name, category, expiry rule, whether a document is required. Same wizard, feeds Manage Ticket Types.
Do this first if your ticket types aren't set up yet — worker tickets are matched against it.

What should the template contain?

This is the choice that decides whether you are adding or correcting. Pre-filled exports carry a locked record ID, so a row that comes back updates the ticket it came from. A blank template has no IDs, so every row creates something new.
Pre-filled with your workers — ticket columns blank
One row per active worker, their details already filled and locked. You fill in the ticket columns. Nobody has to spell a name the way we spell it.
Best for the first load, or a course a whole crew just sat.
Pre-filled with workers and their current tickets
Everything on file today, exported for editing. Change an expiry, add a number, fix a typo, then re-upload — matched rows update rather than duplicate.
Best for a renewal run or a data clean-up.
Blank template — headers only
Column headers and nothing else. For pasting from a subbie's spreadsheet or a training provider's report. Workers are matched on employee ID, then email, then exact name within company.
Every row creates. Rows that can't be matched to a worker are held back as errors, never guessed.
Worker columns to include
Locked, read-only columns — they exist so the person filling this in recognises the row. Editing them changes nothing on the worker.

What the prototype commits to

Nine rules. Each one is a decision someone has to make before this gets built, and each is made here rather than left to the implementation.

  1. Add from the list page is the existing form with a Worker field on the front. Ticket type, number, issued, expiry, issuing body, state, document, notes, and the Save as draft / Publish pair are the worker-drawer form verbatim. One component, two entry points. Two forms would drift within a release.
  2. Worker is multi-select. The real event is a crew of six sitting the same course on the same day, not one person one ticket. Selecting more than one worker turns the number field into one row per worker, because the certificate number is personal and the course is not. One submission, N ticket records.
  3. A pre-filled export is the update path; a blank template is the create path. The difference is a locked Record ID column that only pre-filled exports carry. A row with an ID updates that record. A row without one creates. Nothing is ever matched on a person's name alone to decide between the two.
  4. Worker matching on a blank template is employee ID, then email, then exact name within company. Two candidates is an error row, not a best guess. Getting a licence onto the wrong person is worse than not importing it.
  5. A ticket type that isn't in the catalogue never appears silently. The review step lists the unknown types and offers one checkbox to add them to Manage Ticket Types. Left unchecked, those rows are errors. Free-text ticket types are how a register becomes ninety spellings of "white card".
  6. Blank expiry is derived from the ticket type's rule; a past expiry imports as Expired. An expired licence is not a bad row — it's the reason you're loading the data. Rejecting it hides the risk you bought the module for.
  7. Documents can't come through a spreadsheet. Where the ticket type requires one, imported rows land as Draft — document missing, in the Draft tab that already exists, and are chased from there. Consistent with the standing rule that compliance gates flag rather than block.
  8. The review step is a dry run and the only way to import. Counted as New / Update / Warning / Error, filterable, fixable inline. Skipping the error rows imports the rest. There is no path that writes on upload.
  9. Every import is one reversible batch. The Activity tab records who imported what, when, from which file, with a single undo while the batch is the most recent change to those records.

Statuses, since the tiles depend on them

Valid
Has an expiry date, more than 30 days out.
Expiring soon
Expiry within 30 days. Threshold is a tenant setting, not a constant.
Expired
Expiry in the past.
No expiry
The ticket type carries no expiry rule. Counts as valid, and is why the current page shows 1 total against 0 + 0 + 0.
Draft
Incomplete — missing a required document or number. Not counted in compliance either way.

Open questions

Three things the prototype deliberately shows rather than answers.

  • One importer or two doors? Initial Data Upload in the top right already imports tenant-wide data. Tickets churn forever, so they need an entry point on this page — but that should be the same importer scoped to tickets, not a second codebase. If it can't be, this replaces the tickets section of Initial Data Upload rather than sitting beside it.
  • Who loads a subcontractor's tickets? Today the head contractor keys the subbie's crew. The export/re-upload pair is exactly the shape you'd hand a subbie to fill in themselves — which is a different permission model and probably a different release.
  • Does a ticket expiring stop anything? The register only pays for itself when an expired high-risk licence is visible where the work is assigned — the scheduler, the SWMS, the site sign-in. Flag, don't block, per the standing decision. Out of scope here, but it's the reason this page matters.
