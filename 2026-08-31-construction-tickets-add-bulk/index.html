Four things wrong with column M

All four are why the column is not extended but removed from the export — see What changes below. It is still read on the way in, so existing files keep working.

1One dropdown cell means one ticket per worker. A worker holding a white card, a first aid certificate and an HR licence cannot be expressed. Most workers hold three or four.
2It carries the type and nothing else. No number, no issued date, no expiry, no issuing body, no state. So every imported ticket is a draft shell somebody opens and completes by hand — the importer moves the drawer-by-drawer work, it does not remove it. And with no expiry date, the register still cannot tell you what lapses next month, which is the entire reason to hold the data.
3The workbook already has the idiom and tickets did not get it. Allowances and Form Numbers both say "separated by a comma" and take many values in one cell. Tickets — the column with the dropdown — takes one. Even comma-separation would not be enough here, because a ticket has dates, but the inconsistency shows the column was an afterthought.
4There is no download of your existing workers. The file ships with three dummy rows — James Baker VAR-1, Ford Humphries VAR-2, Matilda Grace Anderson VAR-3 — and blank Company and Role. It is a create-only form. Nothing round-trips, so there is no way to correct at scale, and no protection against a second upload duplicating everyone.

What changes

Not a new importer. The same workbook, three edits:

  1. A locked Record ID column in front of the EMPLOYEES sheet, present only on an export of your real workers. It is what makes a re-upload update instead of duplicate.
  2. A second sheet, TICKETS — one row per ticket, keyed on Employee ID, carrying every field the Add ticket panel has: Ticket Type, Number, Issued, Expiry, Issuing Body, State and Notes, plus a read-only Document column. Nothing about a ticket has to be filled in afterwards by hand. Its own locked Ticket Record ID identifies the ticket.
  3. One download, not a menu. The export always comes down filled with your workers and everything already on their record. There is no blank-versus-pre-filled choice to get wrong: a worker with no tickets simply has no rows on the TICKETS sheet yet, and the same file serves a first load, a renewal run and a clean-up.
  4. Column M is removed from the export. Leaving it in gave the file two places to put a ticket — a dropdown that carries a type and nothing else, and a sheet that carries the whole record — and no way for the person filling it in to know which one we wanted. Tickets now live in exactly one place. Files that still have the column keep importing (see below), but nothing we hand out asks the question twice.
  5. Everything an import creates lands in Draft, in the Draft tab that already exists on the Tickets page, and is published from there once checked. That is what the current template already does, said out loud and applied to both routes.
The download carries the same people as this prototype — the eight workers on the Tickets page, their real employee IDs, and the tickets already on the register. Nothing invented sits beside them, so the sheet and the screen can be read against each other without anyone having to work out which row is a sample.

The built file is real — not a mockup. Download the revised workbook: it is the production template with those edits applied, dropdowns repointed after the column insert, validations widened to 500 rows, a hidden _State lookup added, the empty Pay Category sheet dropped, and every new column carrying a Varicon-authored cell comment in the same voice as the existing ones.

One place for a ticket, and the old one still opens. The template we hand out has no Tickets column — the TICKETS sheet is the only place a ticket goes, carrying type, number, dates, issuing body, state and notes. But the importer still reads a Tickets column when an older saved copy arrives with one, so nobody's existing workbook stops working; those entries become draft shells exactly as they do today, and lose to the TICKETS sheet where both name the same ticket. Removing the column from the export and removing support for it are different decisions, and only the first one is worth making now.

What happens if the same ticket is filled in twice

The realistic failure is not a malicious one. Somebody re-sends the file they already sent, or adds a row at the bottom instead of editing the row we exported, or fills in an old copy of the template that still has a Tickets column. All three have to be safe without anyone thinking about it.

A ticket's identity is its Ticket Record ID. Where that is blank, it is worker + ticket type + ticket number. Everything follows from that:

Same file uploaded twice
Every row carries its Record ID, so the second upload updates the same tickets with the same values. Nothing is created. The importer is idempotent.
Row added by hand instead of edited
No Record ID, but worker + type + number match a ticket already on record — so it updates that ticket rather than creating a second copy.
Two identical rows in one file
Collapsed to one before anything is written, and reported as such in the review.
Same type, different number
Not a duplicate — a renewal. Both are kept, the newer becomes current and the older is marked superseded. Collapsing them would destroy the expiry history, which is the one thing the register exists to hold.
An old copy with a Tickets column
Still imported, so nobody's saved workbook breaks. Where the same worker and type also appear on the TICKETS sheet, the sheet wins — no empty second draft beside the detailed one.
A row deleted from the sheet
Nothing. Deletions are never inferred from an absent row — round-tripping an export loses rows for ordinary reasons.

All of it is shown in the review step before a single record is written, counted under Already on record, with the matched ticket named on each row.

The file says employee; the product says worker. Varicon calls these people workers, deliberately — calling a subcontractor an employee is a characterisation nobody wants in writing. The workbook does not: an EMPLOYEES sheet, an Employee ID column, Employee Payroll Allowance. The prototype's own language is worker throughout and the export filters read Active workers only, but the sheet and column names are left exactly as production has them, because renaming a column in a live importer breaks every saved copy customers already hold. Worth a deliberate decision and a migration, not a quiet edit.
Employment Type or Payment type? The workbook's column is Employment Type, with values Salary, Wages, Casual and Subcontractor. The product calls that a payment type, and so does the export filter in this prototype. Same four values, two names, and the same characterisation risk sitting in the word "employment". Also a decision, and cheaper to make now than after another year of exports.
Two more things in the file worth a separate look. The _Role dropdown carries milan, SagarTestResource and Supervisor 1 — test data in a customer-facing list (this may just be the tenant this copy was exported from — unverified). And _Tickets names its eight types inconsistently: five carry a code, "Working at Heights" and "Driving Licence" do not. Ticket types are about to be matched on their name, so that list wants a tidy first.

What the prototype commits to

Fourteen rules. Each one is a decision someone has to make before this gets built, and each is made here rather than left to the implementation.

  1. Add from the list page is the existing form with a Worker field on the front, in a side panel. Ticket type, number, issued, expiry, issuing body, state, document, notes, and the Save as draft / Publish pair are the worker-drawer form verbatim. One component, two entry points — inline on the worker's Tickets tab where the worker is already known, in the standard right-hand panel from the list page where it isn't. Two forms would drift within a release.
  2. One worker per ticket. A ticket is a record about a person — its number, its certificate and its expiry all belong to that person — so the panel writes exactly one. When a crew of six sits the same course on the same day, that is six rows, and keying them one at a time through this panel is the wrong tool. It is the case bulk upload exists for, which is why the two buttons sit side by side rather than one being a power-user afterthought.
  3. One export, and it always carries Record IDs. There is no blank-versus-pre-filled choice to get wrong. The download comes back filled with your workers and everything on their record, each row carrying a locked Record ID, so what returns updates what it came from. A row you add yourself has no ID and creates — but only after the identity check below, so adding a row by hand still cannot produce a second copy of a ticket you already hold.
  4. Matching a row to a person is employee ID, then email, then exact name within company. Two candidates is an error row, not a best guess. Getting a licence onto the wrong person is worse than not importing it.
  5. A ticket type that isn't in the catalogue never appears silently. The review step lists the unknown types and offers one checkbox to add them to Manage Ticket Types. Left unchecked, those rows are errors. Free-text ticket types are how a register becomes ninety spellings of "white card".
  6. Blank expiry is derived from the ticket type's rule; a past expiry imports as Expired. An expired licence is not a bad row — it's the reason you're loading the data. Rejecting it hides the risk you bought the module for.
  7. Every ticket an import creates lands in Draft. Not only the incomplete ones. An import is somebody else's spreadsheet arriving in your compliance register, and it gets checked before it counts — so imported tickets sit in the Draft tab that already exists and are published from there. Each carries the reason it is still a draft: document missing, no number, expired on arrival, or simply not yet reviewed. This is what the current Employee Upload Template already does with its Tickets column; the rule is now stated rather than buried in a cell comment.
  8. Documents can't come through a spreadsheet. Where the ticket type requires one, the imported draft is flagged document missing and chased from the Draft tab. Consistent with the standing rule that compliance gates flag rather than block.
  9. A ticket cannot be doubled up. Its identity is the Ticket Record ID; where that is blank, worker + ticket type + ticket number. Three consequences, all visible in the review before anything is written: a row matching an existing ticket on those three updates it rather than creating a second; two identical rows inside one file are collapsed to one; and uploading the same file twice changes nothing the second time. The importer is idempotent by design, because the realistic failure is somebody re-sending the file they already sent.
  10. Same type, different number is a renewal — not a duplicate. A worker who re-sits their first aid certificate has two HLTAID011 tickets with different numbers and dates, and both are kept: the newer becomes current, the older is marked superseded. Collapsing them would destroy the expiry history, which is the one thing the register exists to hold. Only an exact match on the number is treated as the same ticket.
  11. A ticket goes in exactly one place. The TICKETS sheet, one row per ticket, carrying the whole record. The Tickets column is gone from the EMPLOYEES sheet in the template we hand out: two places to enter the same thing is a question the person filling it in cannot answer, and the dropdown could only ever carry a type anyway. Nothing is lost — the column never held a number, a date or a certificate.
  12. The review step is a dry run and the only way to import. Counted as New / Update / Warning / Error, filterable, fixable inline. Skipping the error rows imports the rest. There is no path that writes on upload.
  13. Removing the column from the export is not removing support for it. Workbooks already saved on somebody's desktop still have a Tickets column, and they keep importing: those entries still create draft shells. Where the same worker and type also appear on the TICKETS sheet, the sheet wins. Deprecate what we hand out; keep reading what we already sent.
  14. Every import is one reversible batch. The Activity tab records who imported what, when, from which file, with a single undo while the batch is the most recent change to those records.

Statuses, since the tiles depend on them

Valid
Has an expiry date, more than 30 days out.
Expiring soon
Expiry within 30 days. Threshold is a tenant setting, not a constant.
Expired
Expiry in the past.
No expiry
The ticket type carries no expiry rule. Counts as valid, and is why the current page shows 1 total against 0 + 0 + 0.
Draft
Incomplete — missing a required document or number. Not counted in compliance either way.

Open questions

Three things the prototype deliberately shows rather than answers.

  • Answered by the file, not by us: there is one importer, and it is the Employee Upload Template behind Initial Data Upload. It already has a Tickets column. So this is not a new importer — it is that workbook plus a TICKETS sheet and a Record ID, reached by a second door on this page. See Template today. What is still open is whether the Tickets page's door and the Initial Data Upload door share one wizard, or whether the tickets door is a thin scoped version of it.
  • Who loads a subcontractor's tickets? Today the head contractor keys the subbie's crew. The export/re-upload pair is exactly the shape you'd hand a subbie to fill in themselves — which is a different permission model and probably a different release.
  • Does a ticket expiring stop anything? The register only pays for itself when an expired high-risk licence is visible where the work is assigned — the scheduler, the SWMS, the site sign-in. Flag, don't block, per the standing decision. Out of scope here, but it's the reason this page matters.
